# Project working conventions

## Git commits

- Never create a commit unless the user explicitly asks for one.
- Write commit messages like a real student working through the project, while keeping them accurate enough to explain the change.
- Match the tone to the situation: cool, calm, and short during casual work; more rushed or panicked when the user says a deadline, presentation, or submission is close.
- Match the message length to the scope of the commit. Small fixes should have short messages; larger milestones can briefly mention what was finally understood or completed.
- Vary the phrasing. Avoid repetitive corporate wording and rigid Conventional Commit prefixes unless the user requests them.
- Keep the learning voice believable: confident about the architecture, with occasional wording that sounds like the implementation just clicked.

Examples:

- `got the landing page sitting right on mobile`
- `cleaned up the empty routes and kept the php structure`
- `finally figured out the login spacing before the demo`
- `please work this fixes the landing page cache issue`
